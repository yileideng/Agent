# 客户端与 Agent 解耦：面向异构 Agent 的接入中间层

## 一、研究背景

Agent 正在进入各类客户端——内容社区、绘图工具、办公软件，但**客户端与 Agent 的开发依然是耦合的**，由此产生两种重复开发。

一种是**接入上的重复**：客户端每接一个 Agent，都要重写协议解析、流式渲染、工具回调、会话管理；N 个客户端接 M 个 Agent，就是 N×M 套接入代码。

另一种更贵，是**建设上的重复**：每上一个带 Agent 的新场景，业务方就要从零搭一套 Agent——模型循环、工具编排、会话、提示词、业务链路全部重写。

我在小红书实习期间参与过一个创作 Agent：用户说一句话，完成「从相册挑图 → 生成标题与正文 → 发布笔记」。这个 Agent 是从零搭起来的，而 App 本身早就有相册与发布能力。如果按本文的思路，客户端只要暴露 `get_album_photos`、`publish_note` 这类工具，Agent 可以直接复用现成的（平台内置或第三方），**交付物就从「一个 Agent」变成「几个工具接口」**。

## 二、问题定义

| 重复开发 | 现状代价 | 目标 |
| --- | --- | --- |
| 横向：接 Agent | N 个客户端 × M 个 Agent = N×M 套接入代码 | N 种接入 + M 种适配 |
| 纵向：建 Agent | 每个业务场景一套 Agent 栈 | 每个场景只写工具接口 |

本文的基本判断是：不同 Agent 系统的差异只有三点——**客户端工具、系统提示词、客户端侧用户记忆**。其中用户记忆可以拆成「系统提示词注入」和「客户端工具检索（如本地 RAG）」来覆盖，所以问题最终收敛到一件事：**如何把客户端的工具接入 Agent**。

工具接入一旦标准化，「为每个场景造一个 Agent」就不再必要：Agent 变成可替换的通用件，业务方只需要提供工具。

## 三、研究思路

在客户端与 Agent 之间加一层网关（Gateway），由它承担协议翻译、工具转接与会话管理：

```
客户端（能力以工具形式暴露）──统一协议──▶ Gateway ──适配 / 注册──▶ Agent 1..M
                                          │
                                          └── 代持 MCP ──▶ 工具在客户端执行
```

具体由三个机制支撑：

1. **统一协议**：客户端只说一种协议（参照 Zed 的 Agent Client Protocol，协议细节自定义），网关负责翻译成各 Agent 的原生接口；
2. **工具升格**：客户端注册自己的工具，网关把它们包装成标准 MCP 工具，任何 Agent 都能直接调用，而工具执行始终留在客户端（数据不出端、可用登录态）；
3. **适配责任外置**：Agent 提供方自己实现服务端并注册进网关，网关不再为每个 Agent 写适配器——新增 Agent 的成本从「写代码」降为「注册」。

## 四、创新点

| 创新点 | 具体机制 | 预期验证 |
| --- | --- | --- |
| **工具升格**：业务能力即插即用，业务方不必自建 Agent | 客户端只实现注册与回调两个端点；网关代持 MCP Server，把注册的工具转成标准工具供任意 Agent 使用 | 「自建 Agent」与「只写工具」两条路径的工程量对比；客户端接入代码量 |
| **适配责任外置**：降低 Agent 维的耦合 | 网关定义统一的 Agent 运行时接口，外部 Agent 自行实现服务端并注册 | 新增一个 Agent 的代码量与工时对比（有网关 vs 无网关） |
| **跨 Agent 的会话连续性** | 各 Agent 只保留原生会话作加速；切换时按同步游标只注入该 Agent 未见过的历史，失败则按共享历史重建 | 切换成功率、注入历史条数、上下文重建时延 |

## 五、研究意义

- **业务团队**：上新功能不必再养一套 Agent 工程能力，交付物从 Agent 降为工具接口，周期与成本都能明显降低；
- **Agent 提供方**：面向统一协议或自助注册，接入一个客户端不再需要单独联调；
- **用户与平台**：同一套客户端能力被所有 Agent 复用；更换 Agent 时会话与上下文延续，不必重新开始。

## 六、拟开展的工作

1. **机制设计与实现**：统一协议、工具升格链路、切换时的会话增量注入；
2. **实验与度量**：接入成本对比、工具调用全链路时延分解（P50/P95）、切换 Agent 的连续性、并发下的会话隔离；
3. **对比与定位**：与 MCP、Zed ACP、LangChain / Dify / Coze 类平台及 API 网关做定位对比，明确本方案的差异。

进度安排上，先完成机制与可运行原型，再补实验数据，最后成文。

## 七、研究边界

- 不做 Agent 能力增强，不训练模型；
- 不做工具市场，也不做多 Agent 编排；
- 业务逻辑与数据仍留在客户端，网关只负责接入、转接与会话管理。
